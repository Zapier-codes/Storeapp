### Track h — Self-update: the store updates itself without a reinstall *(new 2026-10-08, operator-directed; designed in a docs-only session, nothing below is built)*

**Operator's ask:** new Storeapp features reach people automatically, without uninstalling and reinstalling. (Not React-Native-style code push: Storeapp is native Kotlin, so "OTA" here means the app downloads its own new APK and installs it as an update. **What the code does today (read, not run):** `AppViewModel.checkSelfUpdate()` (`AppData.kt`) asks GitHub for the latest release of `NikhilKain/vyxel-apps` (the original author's repo, not this program's), and the banner's Update button (`HomeScreen.kt`) opens the APK link in the browser (`ACTION_VIEW`). **What the index already carries (read in `ZealotEntry.kt` and Zealot's `docs/catalog_index_v2.md`):** per version `version_code`, `download_url`, `sha256`, `size_bytes`, `signing_fingerprint`, `status`, and `compatibility.min_sdk`. **Android's limits (stated from memory of Android's documentation; each leaf that depends on one must re-check it against the current docs before building):**
- The first self-update on a device always shows Android's own confirmation. Storeapp is not a privileged installer and was not installed by itself.
- From Android 12 (API 31), `PackageInstaller.SessionParams.setRequireUserAction(USER_ACTION_NOT_REQUIRED)` lets a later update install without that prompt, only when the installer is the app's installer of record, the change is an update and Android's other conditions hold. - A build that lacks this code cannot update itself. Everyone on 1.1.4 or older installs the first build that has Track h once by hand; updates after it are in-app.
- **Do not build this track on a release that does not install.** The release it ships on must first be confirmed to install on a real phone (Zealot Task 46c-prov, manifest resource ids), because a self-update path would deliver a broken file to everyone.

**Decision on record (changes Section 2's "No `PackageInstaller.Session` rewrite", for self-update only):** `PackageInstaller.Session` is used for Storeapp's own update and nowhere else. `InstallGateway` and the two `ACTION_VIEW` install call sites for other apps stay as they are. ## 2. Decisions on record

- **Merged-card install target: silent pick, no picker.** When `d.ii.zo`'s dedup layer collapses several sources into one canonical card, tapping "Install" silently uses whichever entry the merge picked as canonical (Zealot if present, else highest stars) — never a source-choice dialog. Matches how apt/Homebrew/multi-repo F-Droid clients (Droid-ify, Neo Store, Obtainium) resolve a package across repos: automatically, with the alternates surfaced as secondary info (`d.iii.zo`'s eventual "About this app" section), not a blocking install-time choice a typical user has no basis to answer ("GitHub vs. F-Droid" means nothing to most people). Also the natural extension of the trust hierarchy `1.a.ii.zi`/`1.b.i.zi` already built: Zealot is the only source with a checked checksum/signing-fingerprint claim, so preferring it when present is reusing an existing trust decision, not adding a new one.
- **No Shizuku.** The existing `ACTION_VIEW`-based install path already works on unrooted devices with no extra permissions. Shizuku would only buy a silent (no-tap) install — a real feature with real setup friction (separate Shizuku/Sui install, pairing, per-app grant) that nothing in this program currently requires. Not built; revisit only if silent/MDM-style install becomes an actual product requirement, as its own separately-scoped leaf.
- **No `PackageInstaller.Session` rewrite.** The current `ACTION_VIEW` install path works; rewriting it buys marginal UX for real risk. `1.b.i.zo` wraps the existing calls, it doesn't replace them. **Amended 2026-10-08 (Track h):** a `PackageInstaller.Session` is used for Storeapp's own self-update only; every other install keeps the path above.
- **No CDN migration `[-]` superseded by Track c.** Originally recorded as: the six existing sources' data (hardcoded CDN base + five live clients) stays exactly as-is, untouched, not re-hosted under Zapier-codes infrastructure. **Superseded, this session:** `cdnBase` becomes one field of tenant config (`1.c.ii.zi`) so new tenants can specify their own metadata source without a code fork. This does **not** re-host or change the existing data — the default tenant's `cdnBase` is seeded with the exact existing hardcoded value, so current behavior for the existing install base is unchanged. Only the *mechanism* (compile-time constant → tenant-config field) changes.
- **BouncyCastle for Ed25519, not platform `java.security` crypto (`1.a.ii.zi`).** Android's `java.security.interfaces.EdECKey` (and the `Signature`/`KeyFactory` Ed25519 support behind it) was only added at API 33, confirmed against Android's own reference docs this session. This module's `minSdk` is 26 (Android 8.0) — relying on the platform provider would silently have no working Ed25519 on every device between API 26 and 32, which is unacceptable for a trust-anchor check specifically (a signature check that quietly no-ops on most of the install base isn't a check). `org.bouncycastle:bcprov-jdk18on`'s `Ed25519Signer`/`Ed25519PublicKeyParameters` are used directly as algorithm classes, never registered as a JCA `Provider` (no need to touch global provider precedence for one narrow check), and work identically across every API level this app supports.
- **No-signup request architecture for `distr`'s fleet dashboard (Track f).** A requester submitting a product request never creates an account or logs in — branding + a contact email in, an emailed artifact/live URL out. `distr`'s existing auth stays exactly as-is for its operator-facing org/billing/portal surfaces; this decision scopes only to the new request-intake surface `f.i`/`f.ii` add, it does not remove auth from anything `distr` already does.
- **Request intake lives on `distr`, never on Zealot.** Corrected this session from an earlier draft: Zealot is the Play-Console equivalent — signing authority and catalog, operator-facing only — and must never be the surface a requester lands on. `distr` already has the org/branding/portal/notification scaffolding a public front door needs; Zealot has none of that and building it there would duplicate what `distr` already does.
- **`distr` gets its own infra, isolated from Zealot's, not shared.** Own `ghcr.io` image, own Render instance, own Postgres/object storage, own Novu API instance/credentials — same deployment pattern Zealot already uses, but as a fully separate deployable, not layered onto Zealot's existing service, database, or Novu pipeline. The two consoles serve different audiences (operators vs. self-service requesters) with different tone and template needs, and coupling their infra would couple their release cycles and blast radius for no actual benefit — industry-standard database-per-service boundary, cross-service data sharing happens only through the signed `TenantConfig` publish, never a shared table or an unverified internal API call.
- **GitHub Releases is the sole artifact store for anything built through Track f.** No APK or build artifact is ever uploaded to `distr`, Supabase, or any bucket this program owns — Storeapp's workflow publishes a GitHub Release per build, and every downstream consumer (webhook, email) carries that release's asset URL, never a copy of the file.
- **Publishing a `distr`-provisioned app to Zealot's catalog is manual-upload-only, never automatic.** A completed `distr` build only ever gets the owner an emailed APK — it does not, by itself, create or opt into a Zealot catalog entry. The owner uploads to Zealot themselves when ready. The sole exception is a developer publishing through Zealot's own authenticated API directly in their own workflow, a distinct trust relationship from anything `distr`'s request flow triggers — see `f.xiv` for the (currently unscoped) auth model that exception needs.
- **Free-tier abuse deterrence is device-fingerprint-based, not account-based**, since `f.i`'s no-signup posture rules out an account as the identity anchor. One free product per recognized device fingerprint; treated explicitly as a fraud-deterrence heuristic rather than a real identity system — see `f.xii`'s own caveats (shared-device false positives, evasion by switching devices) and its privacy scoping (salted-hash-only storage, fraud-prevention-only purpose, disclosed rather than opt-in-gated, under GDPR/ePrivacy fraud-prevention carve-outs and NDPR's lawful-purpose test) before shipping it — real legal sign-off still required, this is a scoping decision, not a substitute for one.
- **Private GitHub Release assets are delivered through a `distr`-hosted signed-redirect proxy, never a direct `github.com` link.** `distr` resolves the short-lived authenticated asset URL server-side at click-time and 302s the browser to it — standard practice for distributing a private repo's artifacts to external users without ever handing them a token.
- **Payment processor: `distr` bills through `B-Pay-backend`, Zapier-codes' own existing billing infrastructure, not a direct Paystack/Flutterwave integration.** `Corrected this session:` B-Pay-backend (`github.com/Zapier-codes/B-Pay-backend`) is a white-labeled payment gateway shell already in use, wrapping Korapay/Paystack/JuicyWay/Payscribe (Remita/Flutterwave being consolidated in) behind its own API and hiding the underlying rail from callers and end users alike; `f.xiii` calls B-Pay's own one-time checkout/payment-link endpoint, never a processor SDK directly. The earlier draft (Paystack primary, Flutterwave fallback, integrated by `distr` itself) was inferred from `Edges_LandingPage`'s own Paystack asset without checking whether the program already had its own billing system — it does, and `f.xiii` should never bypass it.
- **Zealot's direct-publish API exception uses a scoped, hashed API key per developer account** (mirroring `distr`'s own upstream `internal/authkey` convention), served from a dedicated endpoint entirely separate from the manual-upload dashboard flow, so the two authentication paths can never be crossed.
- **Federated catalog (`d.iv.zi`): an aggregation layer, not a `TenantConfig` schema-v2 fan-out.** The leaf's own text offered two options — each tenant's config listing every sibling's `catalog_index_base_url` so the client fetches and Ed25519-verifies N indexes itself, or one extra aggregated index published server-side. Picked the latter: fan-out means every device's fetch-plus-signature-check cost grows with the *total tenant count in the program*, not with anything about that device's own use, and duplicates `1.a.ii.zi`'s verification machinery N times over. Zealot already knows the full tenant set server-side, so it publishes one additional signed index (every tenant's apps, each entry now optionally carrying `tenant_id`) and the client fetches that one extra URL, reusing `1.a.ii.zi`'s trust primitives verbatim. The federation endpoint is deliberately **not** a `TenantConfig` field — it's identical across every tenant by definition, so it isn't that tenant's own data; it sits alongside `ZealotClient.baseUrl` as a second settable, program-wide (not per-tenant) client config, same "blank means not configured yet" posture, since no real federation endpoint exists anywhere in this program yet (Zealot-side publishing work, a different repo).
- **Push is augment-with-fallback and config-gated (`e.i`).** FCM is initialised programmatically from Gradle-property-supplied options (no `google-services.json`), and `UpdateCheckWorker` is kept as the always-on fallback sharing one notification slot with remote push. The client never holds Novu credentials; it only registers an FCM token with Zealot, which owns delivery.
- **Multi-tenant model: single runtime deployable, not fork-per-tenant.** One codebase, one build per repo; tenant identity resolved dynamically (domain-based for D-Store/Zealot, tenant-config-fetch-on-launch for Storeapp) rather than maintaining separate branded forks. Where Android's OS-level constraints make a field truly build-time-fixed (`applicationId`, launcher icon/name), those are isolated to Gradle product-flavor selection (`1.c.i.zo`) and nothing else — everything else (branding shown in-app, CDN/API endpoints, feature flags) is runtime tenant config. Tenant-config schema is explicitly versioned (`schema_version`) and additive-only-with-defaults, so an older client that hasn't updated yet never breaks on a newer config — same posture already committed to for the Zealot index's rotation window.

## 3. Handoff process

Same as D-Store's — but inlined here in full, not just referenced, because a
session (this one) previously read only the one-line summary that used to be
here, skipped opening D-Store's `HANDOVER.md` §3 for the actual mechanics, and
handed off wrong git commands as a result (plain `git diff` + `git apply`
instead of `git format-patch` + `git am`, and apply/push commands with no
concrete paths in them). Read this section itself from now on; don't defer to
D-Store's copy for the mechanics.

**Cross-repo sessions (operator's instruction, 2026-10-07; supersedes the per-repo apply commands below whenever a session
changes more than one repo).** The session hands over **one uniquely named file, `apply-all-<stamp>-<slug>.sh`**, built by D-Store's
`scripts/make-apply-all.sh` (one squashed commit per repo, `git format-patch -1 HEAD --binary --stdout`, Zealot first,
Storeapp's branch is `main`). The operator runs `bash ~/storage/downloads/<the exact file name the session gives>` (`--check` for a dry run; the name is new every delivery, never the bare `apply-all.sh`). It
checks every repo first, applies and pushes each, never forces, and rolls back a failed `git am`. The full rule is in
D-Store's `HANDOVER.md`, "Cross-repo delivery". The steps below still describe a Storeapp-only session and the content
of each commit.

0. **Check upstream first:** `git fetch origin` and compare against
   `origin/main`. If origin has moved since the local clone/session was last
   synced, `git rebase origin/main` before starting the leaf and before
   generating any patch — a patch built against a stale base can fail to
   apply with `git am` even when its content is logically identical to what's
   already there.
1. **Do the one assigned leaf task** (Section 1 — nothing more).
2. **Update this file**: flip the completed leaf's `[ ]` to `[x]`, add a
   **Done note** on what shipped and what's flagged forward. If a leaf can't
   finish in one session, do not commit partial work as done — mark it `[~]`
   instead, with a note on exactly what's left, and commit with a `WIP:`
   prefix rather than the plain leaf-path message below.
3. **Commit** the code change and the `HANDOVER.md` update **together, in one
   commit**, with a message that starts with the leaf path:
   ```
   git add -A
   git commit -m "1.a.i.zo: add ZealotClient index fetch"
   ```
4. **Generate the patch** as a proper `git format-patch` output (an mbox-style
   file `git am` can apply) — **never** a plain `git diff`, which drops the
   commit metadata `git am` needs and isn't what step 6 below applies:
   ```
   git format-patch -1 HEAD -o patches/
   ```
   For a handoff spanning several commits, combine them into one file instead
   of handing off several: `git format-patch origin/main --stdout > patches/000X-<description>.patch`.
   Always hand off exactly one patch file, never more than one.
5. **Hand the patch file to the user** — never push directly unless
   explicitly told to. The patch is the deliverable that closes the session.
6. **Applying it** (next session, or the user, on their own machine) needs
   concrete paths, not bare filenames — state the actual repo path and the
   actual patch path/filename every time, e.g.:
   ```
   cd ~/Storeapp
   git am ~/storage/downloads/0001-1.a.i.zo-add-ZealotClient-index-fetch.patch
   git push origin main
   ```
   It's `git am` here, not `git apply` — `git apply` doesn't work on a
   `format-patch` file's mbox format the same way and won't carry the commit
   metadata through. This repo's default branch is `main` (not D-Store's
   `master`) — don't copy that detail across repos without checking.
